# mkosi image with sysupdate and a core extension

Found in spike #90 (systemd 262, mkosi 27.1, Arch snapshot 2026-11-15), each
verified in a VM. The prototype definition is in `/cache/spike-90/image` on
the host.

## Boot counting needs a writable UKI file

`Mode=0444` in the UKI transfer (`[Target]` of `10-uki.transfer`) sets the
FAT read-only attribute on `homelab_N+3-0.efi`. systemd-boot then cannot
rename it to count a try, never sets `LoaderBootCountPath`,
`systemd-bless-boot` never runs, and a broken image would boot forever.
Leave `Mode=` out of the UKI transfer. Check after an update: the file must
read `+2-1` on the first boot and lose its counter once
`boot-complete.target` is reached.

## Extensions in /var merge too late for the boot transaction

`/var` is its own partition, so the initrd services
`systemd-sysext-sysroot`/`systemd-confext-sysroot` cannot merge from it (the
man page says so). `systemd-sysext.service` merges after PID 1 has built the
boot transaction: a unit the extension enables through
`multi-user.target.wants/` is loaded but never started. The base image ships
`homelab-extension-units.service` (after `systemd-sysext.service`) that runs
`systemctl start --no-block multi-user.target`, which pulls in the new wants.

The same holds for the host confext: `systemd-networkd` (no default
dependencies) starts before `systemd-confext.service`, so network files from
the confext are missed. A drop-in orders networkd `After=systemd-confext.service`.

## No restart fields in the extension

`EXTENSION_RESTART_UNITS=` or `EXTENSION_RELOAD_OR_RESTART_UNITS=` in the
extension-release file deadlock the boot: the merge at boot waits for a
restart job of a unit that is ordered after the merge. Keep only
`EXTENSION_RELOAD_MANAGER=1`; whatever runs `systemd-sysupdate
--component=homelab-core update` restarts the daemon and Caddy itself.
Recovering a host stuck this way needs `systemd.sysext=0` or the symlink in
`/var/lib/extensions` pointed back at the old image.

## Mount namespaces keep the old /usr

A service with its own mount namespace (Caddy runs with
`ProtectSystem=strict`) keeps seeing the previous `/usr` after a refresh.
A reload is not enough; restart it.

## A read-only root needs these on /var

- `/root` is a symlink to `/var/roothome` (made in the finalize script; the
  filesystem package owns `/root`, so an extra tree cannot replace it). nix
  and git write under `$HOME`.
- SSH host keys: `HostKey /var/lib/sshd/...`, generated by a unit;
  `sshdgenkeys.service` masked. Root's key in
  `/etc/ssh/authorized_keys/%u`.
- Machine ID: `/var/lib/homelab/machine-id`, bound over `/etc/machine-id`
  by an initrd service (`homelab-machine-id.service`, after the initrd has
  mounted `/var`); PID 1 keeps a valid ID it finds there. The installer
  writes a random one into each new `/var`. `systemd.machine_id=firmware`
  alone was not enough: `/etc` cannot be written, some boards have an empty
  firmware UUID (a new ID every boot) and others share one. Where the file
  is missing it is made from the firmware's UUID when that is a real one,
  so a host installed before this keeps its ID, and is random otherwise.
  The installer medium keeps none and takes the firmware's on every boot.
- Users and groups only from `sysusers.d` in the base image; an extension
  cannot add one.

## One disk for the root, /var and /nix

A UKI finds its root by the verity root hash, whose halves are the root and
verity partitions' UUIDs; `/var` is mounted by partition label, and `/nix`
is a folder of it (see "The Nix store is on /var").
The installer medium and a disk installed from it have the same labels and,
at the same version, the same root and verity UUIDs, so with both attached
every `/dev/disk/by-partuuid` and `by-partlabel` link has two claimants.
Before this was handled, the medium could mount an installed disk's `/var`
(no installer, no reinstall), an installed host could come up as the
installer from a medium left in, and a root's data and hash could come from
different disks.

The system now uses one disk: the one the boot loader started from when it
has the root, and never the installer medium when another disk has it.

- **udev link priority picks the disk.** udev gives a contested link to the
  device with the highest `link_priority`, and between equals to the one it
  processed last. `usr/lib/udev/rules.d/61-homelab-disk.rules`, in the root
  and the initrd, gives a partition +100 when its disk is marked
  `ID_PART_GPT_AUTO_ROOT_DISK` (in the initrd the disk the boot loader
  started from, in the running system the root's disk) and -100 when its
  disk is the installer medium. Partitions inherit both properties from
  their disk, and fstab stays as it is.
- **The medium is known by its GPT disk UUID**, which repart derives from
  `Seed=` in `mkosi.conf`: the same in every build, on any bus, and no
  penalty for a system installed on a USB disk. `make image-check` compares
  the built image's with the constant in the rule.
- **Priority needs a wait.** It only settles a link among the devices udev
  has seen, and verity setup opens the root as soon as one claimant is
  there: an internal disk is found well before a USB stick. An initrd
  service (`homelab-loader-disk.service`, ordered before
  `systemd-veritysetup@root.service`) waits for the loader's partition, and
  then for the root's link to point at the loader's disk, or, when that disk
  has no root (the boot loader on another disk's ESP), at a disk that is not
  the medium. It gives up after some seconds and never fails the boot.
- **`/var` is mounted in the initrd** (`x-initrd.mount`). udev's link
  database is emptied at switch-root, and a link can point at the other disk
  for a moment while the main system's udev finds the disks again. What is
  mounted from `/var`'s disk later (`/nix`) is found from the mounted `/var`,
  not by a link.
- **The installer runs repart with `--seed=random`.** The default seed is
  the machine ID, so two disks installed on one machine got the same ESP
  and `/var` partition UUIDs.

## A core and the image it runs on

Image and core are released together and update apart: the core without a
restart, the image with one. The one rule between them is that **a core
names the oldest image it runs on** (`HOMELAB_MIN_IMAGE` in its
extension-release, `minImage` in `nix/pkgs/core-extension.nix`; empty for
any). Images try to stay compatible with older cores, without a promise,
and a core does without what an older image lacks rather than not start.
`SYSEXT_LEVEL` stays 1 on both: an extension of another level is not merged
at all, which leaves a host without its daemon.

- **Every boot picks the core** (`homelab-core-update.service`, before
  `systemd-sysext.service`, so nothing has to restart): the newest one the
  image takes, among the installed cores and the newest downloaded one. A
  downloaded core is so in use after any restart, and an image the boot
  loader went back to gets a core that runs on it.
- **The daemon's core update refuses a core that needs a newer image**, and
  an install of both puts the image in its slot and leaves the core for
  that image's first boot.
- **A failed update is rolled back, and not tried again by itself.** The
  image by boot counting. The core by the update's health check, or at boot
  by the boot check, which merges the core before; either writes the
  version to `/var/lib/homelab/core-failed`, which the boot's pick skips.
  A core update asked for by hand tries it again. The file is not deleted
  instead: the release check would download the same core again.
- **An image from before the rule** has no `core-min-image`: the daemon
  then knows no minimum and tries a core as before, with the health check
  behind it.

## The Nix store is on /var

An install first gave the store a partition of its own, 16 to 32 GB, in
front of `/var`. `/var` could not give it room, every stack pins its own
nixpkgs, and nothing removed old systems, so a host with a few stacks filled
it.

- **New installs have no `nix` partition.** The store is `/var/nix`,
  bind-mounted at `/nix` by a generator (`system-generators/homelab-nix`).
  A host installed before keeps its partition: the generator looks for a
  partition named `nix` on the disk `/var` is mounted from, in `/sys` and by
  kernel name, and mounts that instead. A generator runs with a read-only
  file system, so a unit (`homelab-nix-dir.service`) makes the folder.
- **A stack keeps the generation it runs and two healthy ones before it.**
  The rest leave its profile when an update, rollback or start ends; a
  generation that failed its health check goes at once.
- **The store's garbage is collected** two minutes after a stack was updated,
  rolled back or removed, and when less than 8 GB are free (looked at once a
  day; nix collects by itself during a build that leaves less than 4 GB,
  `min-free` in `/etc/nix/nix.conf`).
- **A collection and a build never overlap.** A build's result is in the
  store before the stack's profile names it (`nix build --no-link`), and a
  collection in between would delete it. Builds hold a gate together; a
  collection waits for them and they wait for it.
- **A collection also removes fetched sources**, nixpkgs among them: the
  next build of a stack downloads its nixpkgs again.

What is left: two installs of the same version on fixed disks, started by a
boot loader on a third disk. Neither is the loader's disk or a medium, so
the link goes to whichever udev saw last.

## Building on NixOS: mkosi runs in an Arch build root

mkosi from nixpkgs cannot bootstrap Arch on a NixOS host, with or without a
tools tree: nixpkgs' `pacman-key` reads the keyring from its own empty
prefix, every package scriptlet run through nixpkgs' pacman segfaults (so
the tools tree has no CA bundle), and mkosi's sandbox cannot follow the
host's `/etc/ssl/certs` symlinks into `/nix/store`. `image/build.sh` makes an
Arch build root from the bootstrap tarball of the same snapshot (sha256
pinned) and runs Arch's own mkosi in it under `systemd-nspawn`. It needs
sudo, and lives in `/var/cache/homelab-image`, outside any checkout, since it
is root-owned.

## Verity slots and sysupdate

- Each root slot is a data and a hash partition (`Verity=data`/`hash`,
  `VerityMatchKey=root`); mkosi puts `roothash=` on the UKI and repart
  derives the two partition UUIDs from it. That pins each UKI to its own
  root with no `root=` at all.
- Split files must carry the UUID (`SplitName=root.%U`) and the transfers
  match it with `@u`, or sysupdate writes the slot with a new UUID and the
  UKI does not find its root.
- The installer's `CopyBlocks=auto` copy keeps the UUIDs: a disk installed
  from the running image boots its own verity root.

## Host settings through a confext (#96)

- `systemd-confext refresh` does not see changed files in a directory
  extension: it compares the extension list, not contents. Use
  `--always-refresh=yes`.
- The daemon's umask (0027) makes new directories 0750 root:homelab-daemon.
  Merged over `/etc`, a confext directory takes its own mode, so networkd
  could not read `/etc/systemd/network` (and a top-level `etc/` like that
  would shut every other user out of `/etc`). The applier makes its
  directories 0755 explicitly; its test runs under that umask.
- The kernel's host name is set from the image's `/etc/hostname` before the
  confext merges, so the daemon sets it (`hostnamectl --transient hostname`)
  on every start, not only when the setting changes.
- Arch's base has no `hostname` command; read `/proc/sys/kernel/hostname`.
- A new daemon module needs its name in both `internal/logging` and
  `internal/cmdrunner` (each keeps a list; cmdrunner panics on an unknown
  one, which a fake runner in tests does not).

## Falling back needs the failed boot to end (#97)

Boot counting only counts a try when the machine boots again. A root that
does not mount (a corrupt slot fails dm-verity) leaves the initrd in
emergency mode, waiting for a console nobody watches. The image's initrd
replaces `emergency.service` with a reboot
(`image/base/mkosi.initrd.conf`), and the main system's boot check reboots
on failure; then a broken version is tried three times and the slot before
boots. `make image-check` proves it by corrupting a newly installed slot.

The boot check also waits (up to two minutes) for the daemon once the core
extension is installed: a new image the extension does not work on falls
back too. Its unit needs `TimeoutStartSec=` above that, or the oneshot's 90 s
default kills the check and fails the boot.

## The boot check restarts only a boot that is counted

A reboot helps only while the boot loader has tries to count. Once a version
is blessed its UKI has no counter, and the installer medium's never had
one. With `FailureAction=reboot` on the unit, anything that kept the daemon
from answering on such a version (a full `/var`, a bad `daemon.env`, a
failed migration) restarted the host for ever, with SSH up two minutes per
turn.

So the unit has no failure action, and the script
(`usr/lib/homelab/boot-check`) decides:

- `systemd-bless-boot status` says `indeterminate` while this boot is being
  counted. Only then does a failed check reboot.
- Otherwise the host stays up with the unit failed. The reason is in
  `/run/homelab/boot-check-failed` and on the console (`/run/issue.d`), and
  the daemon reports it once it runs again.
- Before it gives up, the check merges the core extension from before and
  waits again. If the daemon answers on that one it stays, with a note in
  `/var/lib/homelab/core-fell-back` the daemon reads; if not, the newer one
  goes back, so the host is left as it was set.

`make image-check` breaks the daemon and the core extension on a blessed
version and expects the host up both times (step 11).

## Booting another version by hand

systemd-boot's own variables do it: `bootctl set-oneshot` and `set-default`
with the entry's id, the UKI's file name without its counter
(`homelab_<v>.efi`). The daemon reads them from efivarfs and sets them with
`bootctl` (`internal/sysupdates/boot.go`).

- A default set by hand pins the host to that version, so installing a new
  image clears it.
- A version that used up its tries (`+0-3`) still boots when it is asked
  for. It is not counted then, and when it reaches `boot-complete.target`
  `systemd-bless-boot good` renames it to a good one.

## One operation installs a release

The order is the image, the core, then the reboot. The image only fills the
free slot, so nothing runs it yet. The core is merged next and checked on
the running image, where the version before goes back when it does not
start; the host reboots into the new image only after that. A core that
went back leaves the image in its slot and starts no reboot.

## The initrd's storage drivers are named, not found

mkosi's `default` for `KernelInitrdModules=` is a short list, not "what a
disk could be on". Read off a built UKI in November 2026 it gave NVMe, VMD
and usb-storage, with AHCI, virtio and xHCI built into Arch's kernel, and
nothing else: no UAS (most USB 3 enclosures, so also an installer written to
a USB SSD), no eMMC, no RAID or SAS controller, no Hyper-V or VMware disk.
Such a machine starts the kernel and then waits for a root that never shows.

`mkosi.conf` names the rest by path. To see what a build has, look in the
UKI: the modules are an uncompressed cpio after the main initrd, so
`grep -a 'kernel/drivers/scsi/' homelab_<v>.efi` lists them. `image/check.sh`
does that for one module of each kind, and boots with the system disk
behind three of QEMU's controllers (pvscsi, megasas, usb-uas). The check's
OVMF reads none of them, so its boot loader starts from a copy of the ESP on
a virtio disk and the initrd finds the rest. Two emulation quirks: QEMU's
megasas fails FUA writes (the disk is given `dpofua=off`), and its
mptsas1068 comes up in the kernel with no disk behind it, so that one is not
booted.

## A 64 GB disk is 59.6 GiB

The partition minimums added up to 63.4 GiB, so a disk sold as 64 GB was
refused as "smaller than 64 GB". The sum is 58.1 GiB now (ESP 1, two roots
with their verity 8.1, `/var` with the Nix store 49) and the installer's
`MinBytes` 59 GiB. Change a minimum in
`repart.sysinstall.d` and `MinBytes` together; the check plans an install
onto a disk of 64 billion bytes.

## Installing from the stick (#104)

The installer runs repart with `usr/lib/repart.sysinstall.d`, then `bootctl
install`, then copies the running kernel to the target's ESP. Probed in VMs
on 2026-11-18:

- **systemd-sysinstall cannot install this image.** Its `bootctl install`
  writes `/etc/kernel/entry-token` into the new root (read-only, verity),
  even when the file is there, so it fails after copying the boot loader and
  before the firmware boot entry; `bootctl install --entry-token=machine-id
  --make-entry-directory=no` writes none. Its `bootctl link` puts the kernel
  in `/homelab/` with a type #1 entry (`version 1.0.0.1`) that sorts above
  every image version, so it would stay the default after a sysupdate
  installs `EFI/Linux/homelab_V.efi`. sysinstall fits a writable root with a
  verity `/usr`.
- **`bootctl install` sets `default homelab-*`** (its entry token); the
  kernels are `homelab_V.efi`, so the installer sets `default homelab_*`.
- **repart matches existing partitions to definitions by type.** An ESP
  definition with a 1 GB minimum makes repart grow a smaller existing ESP,
  which fails when another partition follows it ("can't fit"). So the
  installer leaves the ESP definition out whenever the install uses an ESP
  that is already there, and a new ESP is exactly 1 GB.
- **An existing ESP needs 400 MB free, not a size.** Two kernels (A/B) are
  139 MiB each at 0.1.0, next to whatever the other system keeps there; a
  300 MB ESP with Windows' files does not hold them. The page refuses an ESP
  smaller than 400 MB from the disk listing, and a plan or an install mounts
  a larger one read-only and measures it, counting this system's own
  kernels from an earlier install as free. Windows' setup makes a 100 MB
  ESP, so free space on such a disk is refused: there is no second boot
  partition (XBOOTLDR) for the kernels. Such a machine takes the system on
  another disk, with that disk's own ESP.
- **`bootctl install --graceful`**: firmware whose variables are full or
  read-only takes no boot entry, and that must not fail an install whose
  fallback loader starts anyway. On an ESP shared with another system the
  fallback loader stays that system's, so the page says to pick Linux Boot
  Manager in the firmware's boot menu, or, without an entry, to add one for
  `\EFI\systemd\systemd-bootx64.efi`. A `linux-generic` definition would adopt
  any Linux data partition on the disk, so `/nix` had its own type GUID, and
  the page refuses free space on a disk that already has root, verity or
  `/var`-typed partitions.
- **The stick and the installed disk share partition UUIDs**: the root and
  verity partitions' UUIDs are the halves of the root hash (and a
  block-copied ESP keeps its UUID: the ESP is formatted new instead). Each
  system still uses its own disk; see "One disk for the root, /var and
  /nix". So the stick boots as the installer next to any install, and an
  install can end in a restart with the stick left in: the installer sets
  the firmware's next boot to the new system's entry (`efibootmgr -n`),
  since a machine set to start from USB would start the stick again. The
  page offers the restart only when that entry was found; turning off is
  always there.
- **A root on a disk without the ESP boots, but nothing mounts the ESP**, so
  the install puts the ESP on the target disk.
- **A `system.hostname` credential loses to the image's `/etc/hostname`.**
  The installer writes the name, with the rest of what the page asked, to
  `/var/lib/homelab/install.json` on the new disk; the daemon takes it into
  the host settings at its first start.
- **The installer-mode daemon must answer `/api/version`**: the boot check
  waits for it, and without it the stick never reaches `boot-complete`.
- **The installer is one browser's, but not for ever.** The first to ask
  gets a token, which the page keeps in `localStorage`, so a closed tab
  comes back to its install. The hold ends when the page has not asked for
  ten minutes (no install running), or when someone types the six-digit
  code the stick's console shows: being at the machine is the proof. A
  restart of the daemon used to be the only way back in.
- **A failed install into free space removes what it made**: the partitions
  that were not on the disk before it started. Otherwise repart refuses the
  next try, which would add the same partition types again. The temporary
  partitions that hold the other free regions are also swept when the
  installer starts, in case it stopped between making and deleting them.
- **UDisks reads a new partition table on its own time.** `udevadm settle`
  returning does not mean UDisks lists the new partitions, so the install
  asks a few times before it reports them missing.

## The medium's size and the console

- The medium (the disk image) is 1.27 GB because its root partition is as
  small as its lz4hc erofs (`Minimize=best`): an install copies it block
  for block into a 4 GB slot, and sysupdate writes an update's root file
  into one, so the slot size lives in `repart.sysinstall.d`, not in the
  image. `Minimize=guess` on the vfat ESP sized it at twice its contents and
  then failed with "Can't fit requested partitions": the ESP has a fixed
  size. `image/build.sh` deletes a version's earlier files first, or
  `SHA256SUMS` lists several roots for one version.
- An install into free space fills the region picked on the page:
  systemd-repart is first-fit, so the other free regions are held by
  temporary `homelab-reserved` partitions while it runs (the plan runs on a
  sparse copy of the table, with `sfdisk` keeping the partition numbers).
- The console is kmscon (`kmsconvt@tty1`, with `getty@tty1` as its
  `OnFailure=`). It runs agetty for the login banner, but agetty clears the
  screen only on a real VT; under kmscon's pty it stacked the banner it
  redraws when the address changes, so `/etc/issue` starts with
  `\e[H\e[2J`. On the plain console a 512-glyph font (Terminus `ter-v`)
  takes the bright-colour bit and garbles coloured text: `ter-i` has the box
  drawing in 256.
- The console units run agetty through `usr/lib/homelab/console-login`,
  which adds `--autologin root` while the installer marker exists. The
  installed disk's `/var` (`repart.sysinstall.d/30-var.conf`) does not copy
  the marker, so only the stick logs root in. That holds because `/var` is
  always the booted disk's: before it was, a host that mounted a stick's
  `/var` logged root in too.
- The first serial port has a login as well: `serial-getty@ttyS0` is
  enabled by preset and runs `console-login`, so the stick logs root in
  there and an installed host asks. No other getty starts by itself
  (`systemd.getty_auto=0`).
- The prompt's icons are literal UTF-8 in `usr/share/homelab/shell.bash`:
  bash expands `$'\U...'` only in a UTF-8 locale, and `/etc/profile.d`
  sets the locale after `homelab.sh`.
- In `image/check.sh`, an ssh opened while the VM reboots hangs forever
  without `ServerAliveInterval`: QEMU's port forward keeps the connection.
- The check attaches the stick as USB storage where it runs next to an
  install: with virtio disks only, every disk appears at once and nothing
  has to wait. To start the stick there, QEMU gives the firmware a boot
  order (`bootindex`). OVMF then deletes the boot entries of every disk
  that has no `bootindex`, the ones an install registered too, so the check
  gives one to each disk attached.

## Releases come through the daemon, not a sysupdate url-file source

A url-file source reads one `SHA256SUMS` for every version in its folder,
and checks it with `systemd-pull` against `import-pubring.pgp`. The release
server keeps one folder per version, whose `SHA256SUMS` covers both the
image and the core extension (`core/…`), and the host also stages its own
builds of main. So the daemon downloads a release (`KindDownload`,
`internal/sysupdates/fetch.go`): it reads `/latest`, checks `SHA256SUMS.gpg`
against the release key built into the daemon, checks every file against
its sum while it downloads into `updates/.download`, and moves the files
into the update folder. sysupdate keeps reading that folder as a
regular-file source with `--verify=no`; a release and a build of main reach
it the same way.

`HOMELAB_RELEASE_URL` and `HOMELAB_RELEASE_KEYRING` in
`/var/lib/homelab/daemon.env` point a host at another server and key; the
image check runs its own server on the build machine (10.0.2.2 from the
VM) with a key it makes.

A build of main is versioned `<newest tag>.<commit time>`: with
`0.0.<commit time>` the first release would sort above every later build,
and a host that installed it would never take a build of main again.

## A fresh host has no age key

Nothing in the image makes `/var/lib/sops-age/keys.txt`, so the daemon
creates it on first start (`agefile.EnsureKey`). Without it every sealed
value (stack variables, channel tokens, backup keys) fails with a bare 500.

## Smaller details

- `systemd-sysupdate` is `/usr/lib/systemd/systemd-sysupdate` on Arch, not
  on `PATH`; `updatectl` is.
- A url-file source may be zstd-compressed (`homelab_@v.root.raw.zst`):
  563 MB instead of the 4 GB slot.
- repart splits free space between every partition with no maximum; give
  the ESP `SizeMaxBytes=` or it takes a share meant for `/var`.
- `UnifiedKernelImageFormat=%i_%v` names the first UKI so sysupdate counts
  it as an instance.
- The build is bit-for-bit reproducible with `Snapshot=`, a fixed `Seed=`
  and `SourceDateEpoch=`, except for `RootPassword=`: a plain password is
  hashed with a random salt every build. Leave it out (SSH keys) or give
  `hashed:` with a fixed hash. Another machine also needs the same tools
  (tools tree from the same snapshot, same mkosi).
- Root's SSH key reaches a fresh image as the systemd credential
  `ssh.authorized_keys.root` (QEMU: `-smbios type=11,value=io.systemd.credential.binary:...`);
  nothing personal is baked in.
- Top-level mount points (`/nix`, `/pool`, `/cache`) must exist in the image:
  the root is read-only.
- Exclude GPU, wireless and sound from `KernelInitrdModules=`: their
